# Dell DW5823e (`8086:7560`), full unlock trace

Traced end to end from Dell's `ModemAuthenticator.exe`, from the threads that
call `DoFccUnlock` to the payloads handed to Windows. Addresses are virtual
addresses in the shipped binary; function bounds come from `.pdata`, and every
instruction listed was reached by walking the control flow from the entry.

| Item | Value |
|---|---|
| Packages | `Dell-Wireless-5823e-and-Intel-L860-R-LTE-Firmware_CXCR2_WIN_6.0.0.19_A01_02.EXE` and `..._WDYFN_WIN_6.0.0.21_A02_03.EXE` |
| Binary | `Production/Windows10-x64/0/Drivers/ModemAuthenticator.exe`, identical in both |
| sha256 | `8c4c8e847b119523e69086cdece9ff2a67829460067061fe1a43591db119c323` |
| Bound by | `Ude.inf`: `PCI\VEN_8086&DEV_7560&SUBSYS_58231028` (eSIM), `SUBSYS_3A171028` (no eSIM), `SUBSYS_00000000` (eSIM) |

On Windows, Intel's UDE driver presents the PCIe modem as an emulated USB
device, `VID_8087&PID_0AC9`, whose interface 0 is the MBIM function. On Linux,
iosm exposes the same MBIM channel as `wwan0mbim0`.

## 1. Callers

`DoFccUnlock` is `0x14000d3f0` (`.pdata` `0x14000d3f0`-`0x14000d4be`, with
chained chunks `0x14000d4be`, `0x14000e088`, `0x14000e0a6`). It returns 0 on
success or "no need", 1 on failure, 2 when already running.

- `DoFccUnlockThread` (`0x1400021c0`): `Sleep(1000)`, `DoFccUnlock`; on 1 it
  logs `FCC unlock failed, times %d/%d` with a limit of 3 and retries while the
  count is at most 3, so up to 4 attempts, 1 second apart. 0 is OK, 2 is
  cancel.
- `PollingFccStatusThread` (`0x140002abe`): waits 1000 ms, calls
  `DoFccUnlock`; while that is nonzero it adds 2000 ms to the wait, capped at
  60000 ms, and calls again.

## 2. `DoFccUnlock`

1. Re-entry guard: if the in-progress flag (`0x1400f6570`) is set, log
   `already in progress, cancel...` and return 2.
2. Find the MBIM interface `VID_8087&PID_0AC9&MI_00` (`0x140003060`). If it is
   missing, log `MBIM interface is not available, retry: %d`, `Sleep(300)`, up
   to 10 times, then give up.
3. Wait for the default modem object (`0x14000d2d0`), up to 50 times 100 ms.
4. **Query.** `Query_INTEL_FCC_MBIM_Extension` (`0x14000e0c0` with `edx = 1`):
   service `{F85D46EF-AB26-4081-9868-4D183C0A3AEC}`, CID 1, empty payload,
   3000 ms timeout, reply into `rbp+0x11a0`.
   - Query failed: log `QueryCommand FAILED, try DO FCC directly` and go on to
     step 5.
   - Otherwise log `Lock mode: %d, Lock state: %d` with byte 0 and byte 4 of the
     reply. If mode is 0, or state is nonzero, log
     `No need to do fcc unlock` and return 0 (`0x14000df75`). Only mode
     nonzero with state 0 goes on.
5. **Challenge.** Log `Modem locked, DO FCC unlock` and
   `Get challenge value from Modem...`. `Set_INTEL_FCC_MBIM_Extension`
   (`0x14000f4e0`) with CID 1 and the 8 byte payload `{0, 0}` (the qword at
   `rbp+0x1a0` is zeroed), reply into `rbp+0x11a0`. Failure logs
   `Get challenge value from Modem FAILED!` and returns 1. The reply is not
   checked further.
6. **Model id.** `DellFccLock::DellFccCheck` (`0x140001d10`). If it passes, the
   14 bytes `DW5823EFCCLOCK` go into the key buffer `0x1400f4510`. If not, the
   buffer is zeroed and `0x140005f90` searches the SMBIOS table from
   `GetSystemFirmwareTable`; if that finds nothing it logs
   `Not find SMBIOS FCC Type.` and carries on with the zeroed buffer.
7. **Hash.** `0x140014080` is SHA-256 (it loads `0x6a09e667`, `0xbb67ae85`, ...
   and finishes in `0x140013c00`); it copies digest bytes 0 to 7, ascending,
   into `0x1400f6870`.
   - `SHA-256(key buffer, 14 bytes)`.
   - Build 8 bytes at `rbp-0x80`: reply bytes `0x11a4`-`0x11a7` (the challenge,
     bytes 4 to 7 of the step 5 reply) then `0x1400f6870[0..3]`.
   - Log `start hash`, `SHA-256(those 8 bytes)`.
8. **Response.** Payload at `rbp+0x1a0`: dword 1 at offset 0, then
   `0x1400f6870[0..3]` at offsets 4 to 7. Byte 0 of the reply buffer is preset
   to 1. Log `Send finial hash value to Modem...`, then
   `Set_INTEL_FCC_MBIM_Extension` with CID 1.
   - Set failed: `Send finial hash value to Modem FAILED!`, return 1.
   - Reply byte 0 is 0: `FCC unlock OK...`, `ResetEvent`, return 0.
   - Otherwise: `Send finial hash value to Modem get response ERROR: %x`, return 1.

## 3. The command path

`0x14000e0c0` takes the service GUID (`CLSIDFromString`), opens a command
session on the modem's device service, and dispatches on `edx`: 1 calls vtable
slot `+0x30` and 0 calls `+0x38` of
`IMobileBroadbandDeviceServiceCommandSession`, which are
`SendQueryCommandAsync` and `SendSetCommandAsync`, matching the two helpers'
log names. `Set_INTEL_FCC_MBIM_Extension` passes an input length of 8 and
copies the response data, when its length is 1 to 0xffe bytes, into the
caller's buffer. That response data is the MBIM InformationBuffer, so byte 0
is the first u32 and byte 4 the second.

In libmbim's naming for CID 1 of this service, the query and set replies are
`{ChallengePresent u32, Challenge u32}` and the set payload is
`{ResponsePresent u32, Response u32}`. Dell's "lock mode" is the low byte of
`ChallengePresent` and its "lock state" the low byte of `Challenge`.

### Confirmed independently by Intel's driver

The same exchange is visible from the other end, in `WinIhvRil.dll` from HP's
L860R+ package sp155280, which translates MBIM into the modem's CSI calls.
`ril_request_INTEL_FCC_LOCK_Set` (`0x180101c70`) requires an 8 byte payload and
branches on its first u32: 0 calls `RemCsiFccLockGenChallengeReq` and 1 calls
`RemCsiFccLockVerChallengeReq`, anything else is rejected. So a set with
`ResponsePresent = 0` is the documented way to obtain a challenge, and
`ResponsePresent = 1` submits the response, from a source with no connection to
Dell. See [8086-7560-hp.md](8086-7560-hp.md).

## 4. `DellFccCheck`

All three must pass:

- `CheckDellPcIdentifyRegistry` (`0x140001560`):
  `HKLM\HARDWARE\DESCRIPTION\System\BIOS\SystemManufacturer` equals
  `Dell Inc.`.
- `CheckSkuRegistry` (`0x140001b60`): `...\BIOS\SystemSKU` equals one of 18:
  `0C00`-`0C09`, `0C0B`, `0C0C`, `0C0E`, `0C1B`, `0C1C`, `0C1D`, `0CD3`,
  `0C1E`.
- `CheckModuleHwid` (`0x140001710`): the module's interface id is checked
  against `PCI#VEN_8086&DEV_7560&SUBSYS_00000000`, `..._SUBSYS_58231028` and
  `..._SUBSYS_3A171028`.

The three subsystems are the same ones Lenovo's `libmodemauth.so` whitelists in
`ApprovedHWIDS` for its own Dell branch.

## 5. Worked form

```
key     = SHA-256("DW5823EFCCLOCK")[0..3]          = bb 23 be 7f
input   = challenge bytes 4..7 of the reply, as sent, || key
digest  = SHA-256(input)
payload = 01 00 00 00 || digest[0..3]
```

## Where the ModemManager dispatcher departs

| Departure | Why |
|---|---|
| mbimcli prints the u32 fields as numbers, so the script swaps to wire order before hashing and back after | The modem hashes the bytes as sent; Dell copies them ascending |
| A query reporting ChallengePresent 0 exits 0 without unlocking | Same as Dell's mode 0 case |
| 3 attempts, 0.5 s apart | ModemManager kills the script after 5 seconds |
| A set reply without a Challenge line fails the attempt | mbimcli prints Challenge only when ChallengePresent is set, so the bytes Dell would hash are not visible |
| The model id is always `DW5823EFCCLOCK` | The dispatcher cannot read the Windows registry; this is the value Dell uses when its checks pass |
