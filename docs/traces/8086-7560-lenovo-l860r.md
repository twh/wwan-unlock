# Lenovo L860R+ (`8086:7560`), full unlock trace

Traced end to end from Lenovo's `lenovo-wwan-unlock` package, from
`DPR_Fcc_unlock_service`'s `main` to the bytes on the AT port. Every step below
was read from the disassembly; addresses are from the shipped, unstripped
binaries. The SIM country and Verizon checks in the dispatch are out of scope
and are only marked where they sit.

| Binary | Notes |
|---|---|
| `DPR_Fcc_unlock_service` | ELF x86-64, BuildID `1ade6fa7129b9aa516fe34757230089e187b81b9`, DWARF, not stripped |
| `libmodemauth.so` | ELF x86-64, BuildID `bf061f9eb89af41fa4302a6b98f3e92f2100f1ae`, not stripped; byte identical to `libmodemauth.so.1.1` |

## 1. Dispatch in `DPR_Fcc_unlock_service`

`main` (`0x3be5`):

1. `get_product` (`0x1e82`) reads `/sys/class/dmi/id/product_family` and
   sets `MACHINE` from a table of ThinkPad and ThinkEdge families (4 to 81).
2. `isWWANModuleInstalled` (`0x2b85`) reads `/usr/bin/lspci -nn` line by
   line. A line containing `7560` and either `Wireless` or `8086:7560` sets
   module code 5 (`0x2dd7`), logged as `WWAN device Intel L860R+ found`. No
   other code is set for that line. The code goes to `-0xc(%rbp)`.
3. For code 5, `main` waits for the device: `deviceExists` is retried with a
   10 second sleep, and after 7 retries it logs
   `Device is not available, Please check driver` and exits 1.
4. The switch on `MACHINE - 8` (jump table `0x7d90`, 74 entries).

Every case was walked with the module code fixed at 5 and every other branch
followed both ways (`mainwalk.py`). Only two cases reach any unlock, and both
call `fccunlock_fm350_l860(1, 5)`, logging `FCC unlock for L860 is triggered`:

| Case | `MACHINE` | Families |
|---|---|---|
| `0x3def` | 8, 9, 15, 16 | X1 Carbon Gen 10, X1 Yoga Gen 7, X1 Carbon Gen 11, X1 Yoga Gen 8 |
| `0x3f0c` | 12, 14, 21 to 26, 48 | L14 Gen 4, L15 Gen 4, T14 Gen 3, T14 Gen 4, T14s Gen 3, T14s Gen 4, T16 Gen 1, T16 Gen 2, P14s Gen 4 |

On every other family, including the Z13 Gen 1, Lenovo's tool does nothing
for an L860R+. No path with code 5 reaches `fccunlock_rw350`,
`fccunlock_rw101` (whose `libmodemauthRW101.so.1.1` has its own
`event_monitor_at`), `setFccUnlock_fxn` or `setFccUnlock_cs24`. The same walk
with codes 4, 6 and 9 does reach those, which is the check that it follows
branches correctly.

Every call site of `fccunlock_fm350_l860` passes selector 1 (`3e1d`, `3e9a`,
`3f3a`, `41f1`: `movl $0x1, %edi`), with the module code in `%esi`.

`fccunlock_fm350_l860` (`0x5344`):

1. `dlopen("/opt/fcc_lenovo/lib/libmodemauth.so", RTLD_LAZY)`.
2. `dlsym` of `get_country_code`, `get_mccmnc`, `init_modemauth_srvc`,
   `init_modemauth_srvc_mbim`.
3. SIM country and, for module 5 only, a Verizon MCC/MNC check (out of scope).
4. Selector 1: `init_modemauth_srvc("/dev/wwan0at0")` (`5840`). Selector 2
   would call `init_modemauth_srvc_mbim("/dev/wwan0mbim0")`, but no call site
   passes 2, so Lenovo's MBIM route is never reached.

## 2. `init_modemauth_srvc` (`0x8083`)

In order:

1. Ignores signals 4, 2, 9, 15, 11, 20.
2. Machine gate. `get_oem_id` returns `dmi_vendor`, which dmidecode's
   `dmi_set_vendor` sets from an exact match of the SMBIOS type 1 manufacturer
   against its `vendor` table (`0x16900`): `HP`/`Hewlett-Packard` 1,
   `HPE`/`Hewlett Packard Enterprise` 2, `LENOVO` 3, `Dell Inc.` 4. If it is
   neither 4 nor 3, `ExecuteCustCmd(1)` runs
   `dmidecode -t 1 | grep 'Manufacturer'` and the output must contain `Dell`
   or `Lenovo` (`strstr_s`, case sensitive); otherwise it returns 1 without
   unlocking.
3. `detect_wwan_module` (`0x7035`): libpci scan, comparing each device's
   **device id only** against the `modules` table (`0x16640`):
   `{0x4d75, 1}`, `{0x7560, 2}`. A 7560 sets `wireless_module = 2`. The
   vendor id is not checked, and the first match wins. This store (`0x711a`)
   is the only write to `wireless_module` in the library.
4. `configure_wwan_sec_key` (`0x7b34`): fills `devCode` from SMBIOS type 133
   (`get_wwan_config_id`, then `ExecuteCustCmd(0)`:
   `dmidecode -t 133`, first string).
5. Model id. `ExecuteCustCmd(1)` again, then `strstr_s(buf, "Dell")`
   (`8277`). `strstr_s` returns 0 when found (`10250`) and `0x199` when not
   (`10247`).
   - No `Dell`: `devCode = "KHOIHGIUCCHHII"` (`82dc`), overwriting step 4.
   - `Dell`: `do_wwan_module_validation` must pass, then
     `devCode = dkey = "DW5823EFCCLOCK"` (`828e`). If it fails:
     `Module validation failed`, return without unlocking.
6. `fork()`. The child makes a GLib main loop and, for `wireless_module == 2`,
   logs `7560 R+ unlock called.` and calls
   `fcc_at_modem_unlock("/dev/wwan0at0")` (`839a`). Module 1 goes to
   `fcc_at_modem_unlock_fm350` instead; anything else `exit(1)`.
7. The parent `waitpid`s. Exit status 0 returns 0. Anything else increments
   `retryCount` and, while it is at most 200, sleeps 3 seconds and forks
   again from step 6.

`do_wwan_module_validation` (`0x7a74`), reached only on Dell machines, for
module 2 requires both:

- `validate_skuid_7560R`: the SMBIOS SKU number contains one of
  `ApprovedSKUIDS`: `0C00` to `0C0E`, `0C1B`, `0C1C`, `0C1D`, `09A1`, `0C1E`.
- `validate_hwids_7560R`: a PCI `8086:7560` whose subsystem is in
  `ApprovedHWIDS`: `0000:0000`, `1028:5823`, `1028:3a17`.

## 3. `fcc_at_modem_unlock` (`0xbe02`)

Its only caller is `init_modemauth_srvc` (`0x839a`). `init_thread_monitor` is
called only from here (`0xbef6`), and GOT `0x15f40`, the `event_monitor_at`
slot, is referenced only by `init_thread_monitor` (`0xbdd3`). The FM350 chain
(`fcc_at_modem_unlock_fm350`, `init_thread_monitor_fm350`,
`event_monitor_at_fm350`) is separate and reached only for
`wireless_module == 1`.

1. `open(path, O_RDWR)`; `tcgetattr`, `c_lflag = 0`, `tcsetattr(TCSANOW)`.
   Failure: `Opening AT interface failed.`, `exit(1)`.
2. `at_open(fd, NULL)` starts the AT reader thread. Failure: `exit(1)`.
3. `init_thread_monitor(fd)` (`0xbdaa`): `pthread_create` with the start
   routine from GOT `0x15f40`, which relocates to `event_monitor_at`, then
   `pthread_join`.

## 4. `event_monitor_at` (`0xb99b`)

`at_send_command_singleline` is called with an empty prefix (`0x11bf0`), so the
first non-final line of the reply is the value line.

| Step | Command | Send | Reply handling | On failure |
|---|---|---|---|---|
| 1 | `at+gtfcclockgen` | singleline | `challenge = strtoul(line + 2, NULL, 16)` | `exit(1)` (`ba58`) |
| 2 | (hash) | | `get_dev_code`, `compute_sha256(devCode, challenge, &resp)` | |
| 3 | `at+gtfcclockver=%lu` (resp, decimal) | singleline | `strtoul(line, NULL, 16) == 1` | send error: `exit(1)` (`bb54`); value not 1: `usleep(3000000)`, back to step 1 (`bd9b`) |
| 4 | `at+gtfcclockmodeunlock` | no result | must be OK | `exit(1)` (`bc2d`) |
| 5 | `at+cfun=1` | no result | must be OK | `exit(1)` (`bca9`) |
| 6 | `at+gtfcclockstate` | singleline | `strtoul(line, NULL, 16) != 0` | `exit(1)` (`bd57`) |

Success prints `FCC lock state: %s` and `exit(0)` (`bd96`).

## 5. `compute_sha256` (`0x6be3`)

```
challenge bytes:  [-0x30] = c & 0xff, [-0x2f] = c >> 8,
                  [-0x2e] = c >> 16,  [-0x2d] = c >> 24     little endian
H1 = SHA-256(devCode, 14 bytes)
H2 = SHA-256(challenge_le[4] || H1[0..3])
out[0..3] = H2[0..3], read back as a u32 on x86, so little endian
```

`compute_sha256_fm350` (`0x6dbd`), used for `14c3:4d75`, stores both big
endian instead. That is the only difference between the two routines.

For `KHOIHGIUCCHHII`, `H1[0..3]` is `3d f8 c7 19`.

## 6. The AT channel

`libmodemauth.so` carries the Android RIL `atchannel`:

- `writeline` sends the command and then `\r` (`0x11b7a`).
- `readline` splits on CR and LF.
- `processLine`: final success is a line starting `OK` or `CONNECT`; final
  error is `ERROR`, `+CMS ERROR:`, `+CME ERROR:`, `NO CARRIER`, `NO ANSWER`,
  `NO DIALTONE`. For a singleline command the first other line that starts
  with the prefix (any line, for `""`) becomes the value line.
- `at_send_command_singleline` fails with -6 when the result is OK but no
  value line arrived (`b673`).
- Neither `at_send_command` nor `at_send_command_singleline` sets a timeout;
  both wait for the final result.

## Where the ModemManager dispatcher departs

| Departure | Why |
|---|---|
| `at+cfun=1` not sent | ModemManager runs the script from its power-up sequence and powers the radio up itself when the script returns |
| `at+gtfcclockstate` logged, not required nonzero | Lenovo reads it after `at+cfun=1`, which is not sent |
| 3 attempts, 0.5 s apart, instead of Lenovo's 3 s restart and 200 forks | ModemManager kills the script after `MAX_FCC_UNLOCK_EXEC_TIME_SECS`, 5 seconds |
| Dell machines take Dell's own MBIM sequence, not this AT one with `DW5823EFCCLOCK` | Dell's tool is the authority for Dell's card; see `8086-7560-dell-dw5823e.md` |
| Model id is the constant, SMBIOS type 133 is not read | Lenovo overwrites the type 133 value on every path that reaches the unlock |
| `bb23be7f` is tried after `3df8c719` on Lenovo machines | Hardware evidence, not Lenovo's code: see below |

## `bb23be7f` on ThinkPads

`bb23be7f` is SHA-256 of `DW5823EFCCLOCK`, the model id Dell's
`ModemAuthenticator.exe` hashes for its DW5823e. Lenovo's library only ever
sends `3df8c719` on a Lenovo machine. Every field report of this unlock working
on a ThinkPad, though, used `bb23be7f`, the key posted in
https://gitlab.freedesktop.org/mobile-broadband/ModemManager/-/issues/751:

- Issue 751: X1, X1 Carbon Gen 10, Z13 Gen 1, T13s Gen 3.
- https://gitlab.freedesktop.org/mobile-broadband/ModemManager/-/merge_requests/1141:
  X1C G10 and two more testers, running a script that sends only `bb23be7f`.

Those scripts never checked the `at+gtfcclockver` reply, so they show the modem
came up, not which key it accepted. Jean Lucas's ModemManager debug log on
!1141 (https://gitlab.freedesktop.org/mobile-broadband/ModemManager/-/merge_requests/1141#note_2385590,
`mm_xmm7560_fcc_debug_2024-04-23.log`) narrows it down. The machine is a Lenovo
(its Ethernet controller carries subsystem vendor `17aa`); the modem reports
subsystem vendor `1cf8`.

- Run 1, 22:12:47: ModemManager's own reader on `wwan0at0` took the reply to
  the script's `at+gtfcclockgen` (`<-- '0xca50dd3b ... OK'`). The script waited
  on its read and was killed at 22:12:52 (signal 9). It never sent a response.
- Run 2, 22:12:55.485: completed in 0.2 s, and at 22:12:55.691 the radio
  powered on.

So the only response that modem received was computed with `bb23be7f`, and it
came up immediately after. Whether it would also accept `3df8c719` is untested.
The dispatcher tries `3df8c719` first, as Lenovo's code does, then `bb23be7f`.
