# HP and `8086:7560`: no host unlock tool ships

HP sells the Intel L860R+ (`8086:7560`) in a large part of its business range, so
an `8086:7560` dispatcher runs on HP machines too. This records what HP's own
Windows packages contain, which is **no host side FCC unlock tool at all**, and
what that does and does not let us conclude.

## HP's subsystems for this module

From linux-hardware.org probes, `8086:7560` appears with three HP subsystems, and
every one is claimed by a package below:

| Subsystem | Machines seen in probes |
|---|---|
| `103c:8507` | EliteBook 840 G6, 840 G7, x360 1030 G4, x360 1040 G5, 865 G9, Spectre x360 13-aw0xxx, Elite Dragonfly |
| `103c:893b` | EliteBook 640/840/845 G9, ProBook 440/450 G9, Elite x360 830 G9, Elite Dragonfly 13.5 G3 |
| `103c:8a53` | EliteBook 645/840/845/1040 G10, Dragonfly 13.5 G4, Dragonfly Folio 13.5 G3, Elite x360 830 G10 |

## Packages examined

| SoftPaq | sha256 (first 16) | `Ude.inf` binds | Host unlock tool |
|---|---|---|---|
| sp138232 | `1c362201f0fc5087` | `8086:7560` SUBSYS `00000000`, `8507103C` | none |
| sp151712 | `1ceababbcee0eba5` | `8086:7560` SUBSYS `00000000`, `893B103C`, `8A53103C` | none |
| sp155280 | `b384dd89ca2d46f5` | `8086:7560` SUBSYS `00000000`, `893B103C`, `8A53103C` | none |

Each is an HP SoftPaq whose payload is appended to the installer stub: a CAB for
sp138232, a 7z for the other two. Their `install.cmd` and `InstallDrv.cmd` only
run `pnputil /add-driver` over the bundled INFs. No unlock binary is installed
and none is invoked.

## The audit behind that claim

An unlock over this service must do three things on the host: hold a 14 byte
model id, compute SHA-256 twice over a challenge the modem picks fresh each
boot, and send the result. Each was tested for, rather than only searching for
names:

| Test | Result |
|---|---|
| Strings `FCCLOCK`, `gtfcclock`, `FccUnlock`, `ModemAuth`, in ASCII and UTF-16 | nothing in any file of the three packages |
| Service id `f85d46ef-ab26-4081-9868-4d183c0a3aec`, as text and as a binary GUID | only `WinIhvRil.dll`, the driver side |
| A SHA-256 constant table (the eight initial values and first round constants) | **absent from every file** in sp138232 and sp151712; in sp155280 only `ThingsMatrixAgentService.exe` has one |
| Imports of Windows crypto (`bcrypt`, `CryptCreateHash`, `crypt32`) | none anywhere, except that same telemetry agent, whose crypto is certificate and TLS work (`CertOpenSystemStoreW`, `BCryptGenRandom`) |
| Services installed by every INF | UDE, ModemControl, IntelGNSS, GNSSVirtualCOMPort, WirelessCCD, FwUpdateDriver with FwSwitchService, FiboConfigSrv, ThingsMatrixAgent, FbWwanFilterService, VirtualNMEAService. No authenticator |
| Callers of the driver's own challenge functions | see below |

A component with no SHA-256 and no crypto API cannot answer a random challenge,
and with no model id there is nothing to hash. The contrast with sp173756 is
direct: that package both carries a SHA-256 implementation and installs
`WWANModemAuthenticator.exe` as the service "WNC WWAN Modem Authenticator".

The driver does not unlock on its own either. In `WinIhvRil.dll`,
`RemCsiFccLockGenChallengeReq` and `RemCsiFccLockVerChallengeReq` have exactly
one caller each, `ril_request_INTEL_FCC_LOCK_Set`, which is the MBIM relay. So
the driver only forwards what some host application sends; nothing in it
initiates an unlock.

The conclusion is therefore that HP's L860R+ modules are not FCC locked, or are
unlocked before the machine ships. It remains an argument from a complete
absence rather than from a positive statement in HP's code, and the one avenue
not checkable offline is whether HP publishes a separate unlock utility outside
these driver SoftPaqs.

For contrast, HP does ship a host unlock tool when a module needs one: the WNC
M80 package sp173756 carries `WWANModemAuthenticator.exe`, whose `CHpFccLock`
class uses the model id `WNCHPCEFCCLOCK`. That binary targets
`PCI#VEN_03F0&DEV_09C8` and `DEV_0800`, not `8086:7560`.

## What HP's driver does confirm

`WinIhvRil.dll` (sp155280, `src/drivers/UDE/`) implements the host end of the
Intel FCC lock MBIM service, and it independently confirms the exchange our
Dell method performs. Addresses are from that build.

`ril_request_INTEL_FCC_LOCK_Set` (`0x180101c70`):

```
cmp rsi, 8        ; payload must be 8 bytes, else "Invalid parameters"
test ecx, ecx     ; first u32 of the payload
je   -> 0x1801020ec  call RemCsiFccLockGenChallengeReq
cmp  ecx, 1
je   -> 0x180101faf  call RemCsiFccLockVerChallengeReq
                     otherwise "Invalid parameter provided by UI"
```

So, in Intel's own driver:

- **set with the first u32 = 0 generates a challenge**, and
- **set with the first u32 = 1 verifies a response**.

That is exactly what Dell's `DoFccUnlock` does and what the dispatcher's Dell
method sends: `--intel-set-fcc-lock=0,0` to obtain the challenge, then
`--intel-set-fcc-lock=1,<response>`. In libmbim's naming the first u32 is
`ResponsePresent` and the second is `Response`. See
[8086-7560-dell-dw5823e.md](8086-7560-dell-dw5823e.md).

`mbim_map_FCC_LOCK_set` (`0x180037920`) agrees on the shape: it rejects anything
whose length is not 8 or whose first u32 is above 1, then forwards the 8 byte
payload with request id `0x273`.

The query side is `ril_request_INTEL_FCC_LOCK_Query` (`0x180101860`) into
`RemCsiFccLockQueryReq`, and the module reports two values that the driver logs
as `fcc_lock_state : %d  fcc_lock_mode = %d`, matching the two fields Dell reads
from the query reply. `WinIhvRil.dll` also carries
`FCC feature supported` / `FCC feature not supported`, so the driver treats the
whole feature as optional per module, and
`FCC is in LOCKED State. Send HW Radio OFF to OS`, which is how a locked module
appears to Windows.

## What this means for the dispatcher

The script cannot gain an HP method, because no HP key or HP sequence exists in
anything HP publishes for this module. An HP machine therefore takes the
dispatcher's "other vendor" path: Lenovo's AT method first (SMBIOS derived model
id, then `3df8c719`, then `bb23be7f`), then Dell's MBIM method.

One open question remains: if an HP module does turn out to be locked, which
model id HP would use. `WNCHPCEFCCLOCK` (`576f0ae0`) is what `CHpFccLock`
returns in HP's shared authenticator, but that binary drives the WNC M80 and
the FM350, not this module, so the value must not be carried over here without
evidence. See [hp-wwanmodemauthenticator.md](hp-wwanmodemauthenticator.md).

Settling either one needs a report from an HP owner: whether the modem powers up
without any unlock, and if not, the dispatcher's log with
`FCC_UNLOCK_DEBUG_LOG=1`, which records each model id tried.
